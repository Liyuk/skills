# PR 同步流程

本项目通过 Pull Request 同步修改。`main` 保存合并后的版本，工作分支保存待审阅内容。本规则取代后续工作中的直接推送方式；早期发布记录保留为历史事实。

## 开始修改

检查工作区和当前分支，获取最新远端状态。从最新 `origin/main` 创建描述任务的分支，例如 `codex/improve-gift-planning`。已有相关且未合并的 PR 时，继续使用它的工作分支。

存在未提交修改时先确认归属并保留，不用重置或清理强行回到基线。需要更新工作分支时使用普通合并；不要重写已推送历史或强推来处理同步。

## 提交与打开 PR

运行 `AGENTS.md` 要求的测试和校验，并按改动检查技能包、来源与插件清单。提交修改后只推送工作分支，创建或更新以 `main` 为目标的 PR。

PR 描述说明问题、修改后的行为、实际执行的检查，以及尚未验证的范围。只改文档时明确说明，不能把历史测试或案例库存当成本轮运行结果。

工作完成的同步交付是可审阅的 PR 链接。若检查失败，报告失败并继续修复；遇到需要用户决定的问题，在 PR 中保留待决状态。

## 后续修复与合并

PR 开放期间的修复、验证记录和文档补充仍提交到同一分支，更新 PR 描述。默认由用户决定合并；只有用户明确授权时，Agent 才能合并或启用自动合并。

合并后获取远端状态；工作区干净时可回到本地 `main` 并仅快进更新。下一项修改使用新的工作分支与 PR。不要将已经合并的分支用于新的提交。

## 本规则的范围

这是仓库与 Agent 的工作约定，现有 CI 已在 push 和 pull_request 时运行检查。GitHub 服务端分支保护属于另一项仓库设置；本文不声称已启用服务端对直接推送的强制拦截。
