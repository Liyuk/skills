# 个人经验 Skills 仓库：技术方案与建设规划

日期：2026-10-14
状态：供讨论的技术方案；尚未实施
第一阶段使用者：自己日常使用，成熟后公开分享

定位修订：**Ask Liyuk 就是蒸馏本人经验与判断方法的核心 skill**，尚未创建。由本人主持经验蒸馏；技能迁移和方法路由是支撑手段。

## 1. 定位与目标

把个人经验转成 AI 能反复执行、能检查效果、能持续修正的方法。来源包括 GitHub 项目、已经写好的 skills、个人博客，以及正在重构的 Interview Book。最终让自己或使用者带着一个具体问题进入 `Ask Liyuk`，得到基于本人已确认方法的理解、追问和处理路径。

一次提炼最终应回答：什么任务需要这项经验？AI 应该先看什么、怎么判断、产出什么？哪些信息不足时应停止下结论？怎样知道这项 skill 比普通提示更有用？

主仓库采用“小能力、独立使用、可以组合”的形式。参考对象已确认为 Matt Pocock。借鉴其从日常工程问题出发组织技能、用统一入口帮助选择技能与流程的方式；具体判断、能力与流程由自己的经验决定。[Matt Pocock 的仓库](https://github.com/mattpocock/skills)

其 [`ask-matt`](https://github.com/mattpocock/skills/blob/main/skills/engineering/ask-matt/SKILL.md) 明确承担技能与流程路由，强调推荐前阅读对应技能入口。Ask Liyuk 的目标由用户进一步明确为“蒸馏我”：将本人理解问题、追问、取舍和验证的方法转为可执行能力，方法路由只是可选支撑。这是本项目设计，不是对 Ask Matt 现有能力的描述。

第一阶段围绕三个实际使用面：

- **工程判断**：技术规划、技术方案评审、指标解释、复盘、汇报。
- **写作与表达**：从口语和零散材料形成文章，保留作者判断，审稿和翻译。
- **专项实践**：从项目中提炼可迁移的方法，例如检索评估、插件边界、路由策略和状态工作流。

面试题系统为以上任务提供检查问题、追问和练习案例。面试准备本身也可以形成独立 skill，但不需要把整套题库搬进来。

### 1.1 Ask Liyuk 的职责

面对自然语言问题，先识别用户要作的决定、已有材料和关键缺口，按本人已确认的方法组织追问、判断、取舍与下一步验证。对“为什么先问这个、为什么这样判断”，给出简短理由，并在需要时指向本人文章或案例。能在当前技能内完成的分析直接完成；专项任务需要其他技能时再连接。

例如用户说“这个项目推进不下去了”，入口根据材料区分方向不清、方案有缺口、容量不足或协作承诺冲突，再选择规划、评审或复盘等方法。它可以先问一个会改变处理路径的问题，避免默认把所有技能串起来。

技术上分为三层：

1. **核心技能**：`ask-liyuk`，执行本人已确认的问题框定、追问、判断、取舍和验证方法。
2. **方法**：工程判断、表达、成长等独立技能，负责完成具体任务。
3. **依据**：精简的本人方法说明、来源记录和案例，按任务需要读取。

已经知道要用哪项技能的人可以直接调用。入口推荐尚未安装的技能时说明安装需求；不能假装已执行。客户端无法自动调用另一项技能时，提供明确的下一步调用方式。

### 1.2 什么算“自己的经验”

本人主持蒸馏，AI 帮助检索、整理、发现重复与矛盾、生成候选和设计验证案例。每项方法的立场、适用条件、例外和最终表述由本人校准。

区分三种来源：本人已确认判断、项目／文章中的事实、AI 提出的待确认概括。只有第一类可以作为“Liyuk 的方法”进入入口的个人参考；其他内容保留归属与状态。本人尚未形成看法的题目，可以给出有来源的一般分析，不能补成“Liyuk 会这么想”。

## 3. 方案选择

| 方案 | 收益 | 代价 | 本轮建议 |
| --- | --- | --- | --- |
| 一个主仓库，内含独立技能目录 | 发现、维护、评测和发布集中；每项仍可单独安装 | 需要处理已有仓库迁移和依赖 | **采用** |
| 各主题继续维护独立仓库，主仓库只列索引 | 专题边界清楚，迁移少 | 更新和安装分散，重复工具难统一 | 作为过渡兼容方案 |
| 先建知识库、向量检索和自动生成平台 | 大量素材检索方便 | 工程投入较大，仍需人工判断方法是否成立 | 在素材规模和使用需求证明必要后再评估 |

第一阶段的技术主体是 Markdown、版本管理、少量校验脚本和行为评测。源材料留在原项目；主仓库保存经过提炼的指令、必要参考和来源记录。

## 4. 哪些已有 skills 可以加入

### 4.1 优先：五项工程判断技能

保留现有名称和任务边界：

| 技能 | 日常入口 | 迁移重点 |
| --- | --- | --- |
| `tech-planning` | 要形成技术投入与方向规划 | 保留业务目标、备选投入、优先级和停止条件 |
| `tech-review` | 已有方案需要评审 | 保留原文依据、影响和建议动作；按请求决定是否另行修改 |
| `metric-decision` | 数字变化正在推动决定 | 保留口径、可比性、归因和结论边界 |
| `management-retro` | 已完成工作需要复盘 | 保留可验证的下一轮行为变化 |
| `eng-reporting` | 已有判断需要交给决策者 | 保留读者、决定请求、证据和行动 |

现有仓库的评测与来源记录应随迁移保留。迁移前记录版本；迁移后先做行为回归，再修改措辞和结构，避免把迁移与方法重写混在一起。

### 4.2 第二批：博客中的自有写作能力

优先考虑 `shuorenhua`；再评估 `humanize-writing`、`write-writing`、`xinda-ya-translation`。将它们区分为去模板表达、个人口吻校准、从材料起草、忠实翻译几种任务。

`content-review` 与博客集合、发布脚本和编辑规则结合较深，先保留为站点专用能力；若日常有跨项目需求，再拆出通用审稿部分和博客适配部分。`write-research`、`write-projects`、`write-consulting`、`write-gallery` 也按真实调用需求逐项处理。

个人口吻需要标明“适用于自己的内容”，公开后使用者可替换参考。去模板表达可以通用；它不应把所有人的文字改成同一个人的声音。

### 4.3 后续：其他个人主题

`interaction-risk-analysis` 可保持独立主题。它与工程评审共享证据意识，但具体情境、判断方法和输出不同。第一阶段先完成高频工程与写作能力，其他主题按使用频率推进。

## 6. 博客与 Interview Book 如何互补

三类内容分别维护自己的正文：

| 载体 | 主要职责 | 可提供给 skill 的内容 |
| --- | --- | --- |
| 博客 | 解释经验形成过程、立场和案例 | 决策条件、取舍、反例、适用边界 |
| Interview Book | 用问题启发检查、复习和自查 | 主问、追问、考察意图、关联能力 |
| Skills 仓库 | 引导 AI 完成一个实际任务 | 输入要求、动作顺序、判断分支、输出和验证 |

例如“技术规划”文章说明为什么技术投入需要联系业务；Interview Book 可以追问“资源只能支持两件事时如何排序”；`tech-planning` 把这些转成面对当前目标、容量和约束的规划动作。

八个能力域可以用作来源索引和覆盖检查，技能目录仍按任务命名。不预先创建八个空 skill，也不直接用题目关键词决定触发。

面试系统最适合先提供两种候选方法：

- **`experience-review`**：针对用户提供的项目经历，检查事实、个人贡献、判断、取舍、行动、结果与证据，提出少量关键追问。把没有材料的位置留作未知。
- **`interview-preparation`**：按目标岗位和责任范围，从已整理材料选问题、安排练习、记录待补知识。与经历审查区分“选择练什么”和“检查已有表达”。

第一阶段先完成 `experience-review`，待题卡结构稳定后再做题库选择工具。它审查用户提供的经历与表达；人的整体能力、录用、晋升等决定仍需要额外证据和相应判断。

博客、题库与 skill 相互引用来源 ID。某项方法发生变化时，维护者收到影响清单，再分别决定更新内容；不同载体不自动覆盖对方正文。

## 7. 建议仓库结构

```text
skills/
├── README.md                     # 按实际任务列出成熟技能及使用示例
├── LICENSE                       # 在来源核对后选择仓库许可
├── CHANGELOG.md
├── skills/
│   ├── ask-liyuk/                 # 核心技能，承载本人已确认的判断方法
│   │   ├── SKILL.md
│   │   └── references/            # 按问题读取的个人方法、案例及可选路由索引
│   └── <skill-name>/
│       ├── SKILL.md               # 触发描述、必要动作与边界
│       ├── references/            # 按任务分支读取的方法与来源
│       ├── scripts/               # 有实际必要时加入确定性工具
│       ├── assets/                # 有实际必要时加入产物模板
│       └── agents/openai.yaml     # 可选的客户端元数据
├── catalog/
│   ├── sources.yaml               # 来源、版本、公开状态、许可、指纹
│   └── skills.yaml                # 分类、成熟度、来源关系、兼容状态
├── evals/
│   ├── cases/<skill-name>/        # 输入、检查标准、必要测试材料
│   └── reports/                   # 选定的可公开验证记录
├── docs/
│   ├── planning/
│   └── distillation/              # 候选方法卡与提炼记录
└── scripts/                      # 校验、打包、索引与来源变更检查
```

以上是目标结构，按阶段创建需要的文件。只有通过评测并适合安装的目录进入 `skills/`；候选文字放在 `docs/distillation/`。

技能包采用 Agent Skills 的 `SKILL.md` 格式及按需加载的资源目录。`name` 与目录一致，`description` 说明实际任务与触发条件。[格式规范](https://agentskills.io/specification)

### 7.1 独立安装与共享文件

每个可安装技能依赖的本地文件必须位于该技能包内。现有 `tech-review` 引用 `../../agent/decision-and-review-contract.md`，迁入时应把所需内容移至技能自己的 `references/` 并更新链接。

`ask-liyuk` 独立安装后应能完成其声明范围内的个人方法分析，所需方法与参考随包提供。需要组合使用其他技能时检查可用性与客户端能力，不承诺其他技能也已安装。可选路由索引由技能目录生成，详细行为以被推荐技能的实际入口为准。

第一阶段优先保持自包含。确实有多项技能共享、且频繁更新的规则时，可以维护一个源模板，再由打包脚本生成各包内副本，并校验它们与模板一致。生成副本明确标注来源，维护者只编辑模板。暂时不建立复杂的技能依赖解析器。

### 7.2 来源索引

`sources.yaml` 为每项实际使用的来源记录：`id`、类型、仓库 URL、文件路径、上游 commit、本地内容指纹、公开／草稿状态、作者／许可、定位章节、采集日期及被哪些 skill 使用。

本地未提交文件使用内容哈希和工作区状态标识，不能把当前 HEAD 当作该文件的准确版本。博客中英文兄弟文件引用同一逻辑文章 ID，默认以中文原作提炼。

原文留在来源仓库；可安装包内保存运行所需的精简方法。外部链接用于追溯和继续阅读，基本执行不依赖原网站在线。素材许可按文件核对，第三方全文和受限内容不因迁移而自动获得新许可。

### 7.3 技术栈

数据与指令用 Markdown / YAML；校验和索引用 Python，沿用现有工程技能仓库的工具思路。需要可靠解析 YAML 时声明相应依赖，避免用正则代替解析。Git 管理方法演进，成熟后用 GitHub Actions 执行结构、链接和打包检查。

不在 skill 中硬编码个人本地绝对路径或特定模型版本。源码输入来自显式给定的工作区、URL 或材料；缺少工具时清楚说明可继续做的分析范围。涉及运行脚本时声明环境要求。

安装先验证单个技能目录复制及当前使用客户端的发现行为，再评估通用安装器与其他客户端。格式遵循规范和不同客户端实际行为兼容分别记录；不能只通过文件校验就宣称全平台已验证。

## 8. 经验提炼流程

```text
来源登记 → 任务与案例筛选 → 方法卡 → 候选 SKILL.md
        → 新案例对照 → 自己真实使用 → 成熟目录 → 持续修正
```

1. **选任务。** 优先选择近期反复遇到、每次都需要重新解释方法的问题。
2. **选来源并还原经历。** 看实际决策记录、代码、实验和文章；让本人说明当时首先注意到了什么、排除了什么、为什么这样取舍、后来哪些判断被证实或推翻。
3. **本人校准方法卡。** AI 先提出输入、关键判断、有效条件、反例、输出和验证办法的候选整理。本人指出哪里符合经验、哪里是事后合理化、什么情况应改变方法；确认后再包装 skill。
4. **转成执行指令。** AI 负责材料理解、追问和判断；脚本负责确定性的解析、校验、统计和索引。
5. **用新案例检查。** 至少包含来源之外的正常案例、信息不足案例、边界／反例；检查方法能否迁移。
6. **真实使用并修正。** 记录有用的判断变化、错误和额外成本；达到验收条件后进入成熟目录。

同一主题在博客、项目和题库出现时，以任务边界合并候选，保留多来源关系。一次失败先判断来自数据、工具、模型还是 skill，再决定是否改指令，避免每次都增加永久规则。

每轮蒸馏选一个真实经历深入整理。建议保留一份原始叙述、一份本人确认的方法卡，以及两个具有不同约束的新案例。入口中的个人原则从这些已确认方法归纳，不先写一整套抽象人格或价值观，再让案例配合它。

## 9. 评测与维护

结构检查覆盖 frontmatter、唯一名称、目录匹配、本地链接、包外文件依赖和打包完整性。脚本检查使用小型可重现输入验证结果。

行为评测关注 skill 是否改变了实际判断：

- 能否选对任务，信息不足时能否指出真正影响决定的缺口。
- 是否保留事实、责任主体、数字关系和来源。
- 能否在反例中调整判断；方案足够好时能否给出通过结论。
- 输出是否让用户获得下一步动作，是否引入过多追问、流程或篇幅。
- `ask-liyuk` 是否框定了正确问题、选择了合适方法；是否把待确认概括或一般知识错误归为本人观点。

个人判断的验证还需要本人回答：“这个追问和判断是我会作的吗？条件改变后我会怎么处理？”评测同时记录任务效果与个人方法一致性，避免只检查文字像不像本人。

对比“普通提示”和“普通提示＋skill”，固定模型版本、输入、可用工具和材料，并记录差异。迁移回归复用现有案例；新技能建议从 3–5 个有区别的案例起步，再用真实失败补充。它们是有限验证，不能证明普遍有效。

第一阶段手工运行行为案例，自动执行结构校验。使用哪个模型、是否自动运行付费评测、结果记录在哪里，都通过显式配置控制。评测报告记录检查项与失败原因；LLM 评分可辅助，关键行为由人工复核。

来源指纹变化时生成“哪些技能可能受影响”的清单。维护者查看差异、更新方法和相关案例；来源更新不自动发布 skill。

## 10. 已有仓库迁移策略

推荐最终由本仓库维护迁入技能；旧仓库保留历史版本、案例和迁移说明。第一阶段在新仓库完成迁入试验，不改变旧仓库现有发布入口。

迁移步骤：记录来源版本与本地状态 → 复制选定技能和必要资源 → 修复包外引用 → 保留案例和许可 → 回归检查 → 在自己环境试用 → 决定切换主维护仓库。

同名旧版与新版只安装一份，避免发现时出现两个入口。切换时记录安装来源，保留可回退的旧版本。多主题是否都需要独立专题仓库，等公开发布时再决定。

## 11. 建设阶段与验收

### 阶段 A：建立可用底座

初始化主仓库、来源与技能目录；迁入五项工程技能；完成独立安装校验和现有案例回归。同时由本人选取两到三个最有代表性的真实问题，校准第一版 `ask-liyuk` 的入口判断和路由。盘点博客技能的作者、许可和外部依赖。

验收：五项能力各有可运行入口、必要参考和来源；单项安装没有本地断链；现有检查无未解释回归；入口能把代表性问题引向合适方法，并在方法缺失时说明限制；本人认可入口的关键追问与判断。

### 阶段 B：建立第一次完整提炼循环

加入 `shuorenhua`，按真实需求迁入一项作者写作能力；从博客与 Interview Book 共用素材提炼 `experience-review`；从工程项目提炼 `retrieval-evaluation`。

这批覆盖“已有技能迁移”“文章与问题转成方法”“项目实验转成方法”三条路径。数量随实际任务调整。

验收：每项新增能力有来源之外的行为案例；记录普通提示与 skill 的差异；真实使用中能说明它改善了哪一步判断、有哪些限制。

### 阶段 C：按使用记录扩展

从候选表选下一项高频能力，逐个完成提炼循环。补充来源变更检测、兼容性记录和简洁目录。题卡结构稳定后，再考虑自动选题与跨载体索引。

验收：新增技能任务边界清楚，重复能力被合并；每项能独立安装；方法变更有对应案例。

### 阶段 D：公开分享

整理 README 的任务入口、输入输出示例、安装方式、许可和验证范围；保留简洁的中英文发现描述，长正文按实际受众决定是否翻译。发布前检查安装产物不包含私人案例、原始公司材料或本机路径。

验收：另一份干净工作区可以只安装一项技能并完成示例；明确列出已验证客户端与限制；原有专题仓库的维护去向清楚。

## 12. 本方案的第一步建议

先从一个“别人经常来问自己”的真实问题开始，由本人主持还原和方法确认，再完成阶段 A 的入口与能力底座。用阶段 B 验证提炼方法是否有效。核心指标是这些 skill 是否减少自己重复解释方法的次数，是否在新的任务中帮助形成更可靠的判断和动作，以及是否保留了本人处理问题的关键方法。

下一轮从已有项目、博客与面试材料选出代表性经历，整理第一批本人判断方法并由本人校准。首批写作技能、检索评估候选与旧专题仓库切换时机，可在使用过程中继续确定。
