# 经验蒸馏：从经历到条件化方法

归属：作者主持、事实与候选分开、例外验证及明确确认来自本项目用户授权的设计。下面的访谈、证据与方法版本步骤为AI提出的执行方案，尚不能视为Liyuk个人经验规律。

## 先分清三层

经历是发生或被回忆的事件；解释是为什么可能得到该结果；方法是下次在什么条件下采取何种动作。三者不能因为写成顺畅段落就合为事实。

有当时材料时，定位决定之前知道的信息、选项和行动；只有回忆时标明回忆来源，不编记录日期或置信度百分比。结果好只支持结果描述，不能单独证明某一步是成功原因。

## 按材料选一个起点

| 材料 | 先做什么 | 可交付状态 |
| --- | --- | --- |
| 抽象口号 | 找一个能说明它的真实决定 | 观点与待问问题 |
| 有经历但缺选择过程 | 还原当时约束和被放弃的路径 | 事实摘要、候选解释 |
| 有决定与结果 | 比较替代解释，提取有条件动作 | 候选方法卡 |
| 同类多个经历 | 找重复条件和反例，而不是投票 | 范围更明确的候选 |
| 作者对具体方法已确认 | 保留确认对象和例外，再起草技能 | 已确认范围的执行草案 |

作者说“我一般这样做”支持其自述方法，不证明对所有用户都有效。赞同示例措辞不等于认可全部泛化规则。

## 提炼一个可执行分支

描述任务 → 所需输入 → 观察条件 → 动作 → 怎样验证 → 什么时候改选择。优先找到会改变决定的条件，避免写成“先思考、再行动”的通用建议。

例如“先MVP”需要追问：当时哪个未知必须验证？小范围产物能验证吗？失败成本和全量约束是什么？提出缩小验证的候选后，也检查不可拆分任务和已有明确规格的反例。只有上下文支持时才保留该方法。

## 反例如何修改方法

构造一个可迁移的新情境，再构造一个会使原动作失效的情境。明确它们是假设，不冒充本人案例。作者反馈可以导致缩小范围、增加条件、改变动作、撤销候选，或只保留来源观点。

测试否定假设时更新方法卡的适用条件和状态；不要补一个永久例外来保住每个结论。新素材只有在真能改变方法时才继续收集。

## 确认与文件状态

记录作者明确认可的原子判断、适用范围、例外与日期；不要把对整理工作的授权当成方法认可。未确认AI概括始终保留candidate，即使公开发布preview，也不成为author-confirmed。

文件生成按用户约定位置执行。草案写入、成熟技能替换、安装和发布是不同动作，分别遵守已有授权。整合前检查已有技能是否已处理同一任务；来源不同不自动需要新技能。

交付方法卡及最重要的待确认问题，说明每个动作改变了什么判断、还缺什么证据。文本像作者不是确认或有效性证据。
