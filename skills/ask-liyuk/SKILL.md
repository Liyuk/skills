# Ask Liyuk

帮助用户找到适合当前问题的方法。整个仓库承载 Liyuk 的经验；这个入口说明路径，具体判断由对应技能完成。

## 先判断用户要解决什么

读用户已有材料，确认他想作的决定或得到的产物。目标清楚时直接推荐；仅在一个缺口会改变路径时先追问。不要要求用户先填完整问卷，也不要把所有方法串成必经流程。

阅读 [方法地图](references/method-map.md) 选择能力。地图只作导航；说明某项技能的实际行为或建议跳过步骤前，读取该技能可用的 SKILL.md。没有安装时说明暂只能根据地图推荐，不假装已经加载或执行。

## 任务路径

- 未来投入怎么选：tech-planning。
- 已有方案能否支持决定：tech-review。
- 数字变化意味着什么：metric-decision。
- 已完成工作如何改进：management-retro。
- 已有结论如何表达：eng-reporting。
- 项目经历是否讲清贡献、取舍和证据：experience-review。
- 本人要把真实经历提炼成新方法：建议用户主动调用 distill-experience。

多个任务有关时，只说明必要顺序，例如先核对指标，再形成投入选择，最后整理汇报。用户明确要求完成任务，且宿主支持调用对应方法技能时，可以在已授权范围内继续；否则提供可复制的调用提示。仅问“该用哪个”的用户得到推荐即可。distill-experience 是用户主动调用入口，不能代用户启动。

## 输出

通常几句话足够：当前问题的理解 → 推荐方法及理由 → 可直接使用的提示。明确已有方法覆盖范围；目录没有相应能力时说明缺口，可给一般分析，但不能把它称为 Liyuk 已确认的观点。

不扮演真人，不编造 Liyuk 的经历、私人立场或认可。引用本人方法时定位到已提供的技能或来源；当前问题的事实与来源中的经验分别表达。
