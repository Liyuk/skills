# 技术规划示例

## 缺少基线时规划重构

**输入**：希望用 React 重写旧页面并引入微前端，理由是技术栈老旧、体验和效率会改善；没有用户任务基线、维护成本或团队容量数据。

**可用规划判断**：

- **已知**：提出了技术改造方向；具体系统现状和改造范围仍需核对。
- **待验证**：用户体验是否受技术栈限制、迭代效率是否为主要瓶颈。
- **待补数据**：受影响用户任务、当前性能/故障基线、需求交付周期、迁移与双轨维护成本、团队容量。
- **建议**：先选一个代表性页面或用户任务建立基线并比较渐进改造、局部替换和整体迁移。只有验证出系统性瓶颈后，再规划扩大范围。
- **决策条件**：给出估算公式和输入来源；没有输入时不填写 ROI、人数、节省比例或量化目标。

## 两项工作竞争有限容量

**输入**：业务希望建设实验平台，SRE 希望降低事故风险；团队容量有限，双方都标记为 P0，但没有事故损失或实验效率数据。

**可用规划判断**：先把容量、事故影响和实验流程基线列为待确认，再比较最小风险缓解与一次增长验证是否可以组合、缩小或错开。若严重事故风险有证据支持，先处理已验证风险；否则不因标签自动排序。记录由谁裁决、延后工作的代价，以及什么证据会触发重排。
