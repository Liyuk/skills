# Method sources and limits

Use these sources when someone asks why this skill checks scope, evidence, findings, or follow-up. They are method precedents, not evidence that this skill improves review outcomes. Routine reviews do not need citations.

## Sources

| Source | What it supports here | Limits |
| --- | --- | --- |
| [NASA NPR 7150.2D, §5.3](https://nodis3.gsfc.nasa.gov/displayDir.cfm?Internal_ID=N_PR_7150_002D_&page_name=Chapter5) | Planned software peer reviews use checklists or formal reading, readiness/completion criteria, tracked actions, identified participants, and recorded results. This supports scoped checklists and follow-up as review practices. | NASA requirements apply within NASA's governance context. They do not require every team to use a particular checklist, severity scale, or pass label. |
| [Fagan, “Design and code inspections to reduce errors in program development” (1976)](https://doi.org/10.1147/sj.153.0182) | Describes a formal inspection process with preparation, inspection, rework, and follow-up. It is historical grounding for treating review and revision as distinct activities. | It studies formal design/code inspections, not AI-assisted proposal review or this skill's effectiveness. |
| [Gerrit Code Review: Design Docs](https://gerrit-review.googlesource.com/Documentation/dev-design-docs.html) | Gives a practical design-doc structure around use cases, acceptance conditions, alternatives, trade-offs, and decision rationale. | This is Gerrit's own workflow guidance, not a universal proposal-review standard. |
| [Google Engineering Practices: What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html) and [review comments](https://google.github.io/eng-practices/review/reviewer/comments.html) | Supports making review scope explicit, grounding comments in facts, and distinguishing required changes from optional suggestions. | These pages address code changes. Apply the review discipline by analogy; they do not prescribe conclusions for investment or architecture proposals. |

## How to cite these sources

Describe a source as precedent for a bounded practice, then name its context. Do not attribute this skill's output structure or verdict labels to a source unless the source states them. These references do not establish a universal pass threshold, a general severity scale, or an empirical benefit from using this skill. Claims about effectiveness need evaluation of actual users and tasks.
