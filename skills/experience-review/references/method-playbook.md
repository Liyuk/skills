# 经历 Review：把行动、判断和证据连接起来

归属：背景—问题—选择—判断—行动—结果与证据、个人／团队分工、按责任范围选问题，来自公开自查文章。以下检查路径与证据分层是任务化整理，不是人员评级标准。

## 从材料建立判断链

先识别用户要审阅的主张，例如“我主导架构改造”“我推动跨团队上线”“我提升了团队指标”。把每项主张对应到背景、个人动作、实际决定和可核验材料。

“实现了接口”可以直接支持实现职责。要说明判断力，再追问当时卡在哪里、比较过什么、为什么选择某个边界、如何验证。实现规模小也可能有实质取舍；动作多不自动证明判断强。

## 不同缺口，追问不同

| 缺口 | 优先追问 | 不应自动推导 |
| --- | --- | --- |
| 背景大但问题不清 | 哪个用户／系统问题必须改变，不做怎样 | 项目大就有价值 |
| 团队结果明显，个人归属不明 | 自己具体负责、决定与推动哪部分 | 团队收益全部属于个人 |
| 结果有数字，口径未给 | 基线、窗口、负载和同时变化的因素 | 已证明个人净增量 |
| 有职责，无取舍过程 | 一个亲自判断的节点与备选理由 | 只做实现就缺乏判断能力 |
| 定性结果，无数值 | 哪个产物、使用或行为变化能核验 | 必须编数字才有说服力 |
| 失败案例 | 当时判断依据、改变什么、后续是否有证据 | 失败意味着整体能力低 |

一次审阅只追最影响主张的缺口，不让全部知识主题变成问卷。

## 证据可以支持到哪里

用户回忆支持“据本人叙述”；代码或文档支持明确动作／设计，不自动证明上线效果；测试支持其条件下的结果，不自动证明生产收益；指标支持定义与窗口内的变化，因果与个人贡献需要另行依据。

证据冲突时并排呈现来源和条件，不能选好看的数字。没有完整记录可以诚实表达目前可确认的事实，剩余关键问题保留；不要求为自查提供私人档案。

## 按责任范围选择深度

小任务关注问题理解、实现和验证；负责项目关注取舍、依赖与闭环；经营方向关注连续选择与校正；管理经历关注怎样通过目标、支持与授权使他人形成结果。它们是选问题的视角，不是公司的职级分数，也不必每个人都走管理路径。

## 结束与交付

先说当前材料能支持什么，再指出会改变结论的少量缺口与补证方法。仅 review 时不写成稿。用户要求改写时只用已提供事实，推断与待确认不能变成更肯定的文案。

材料足够支持用户当前范围的表达，可以明确说没有发现阻塞缺口；不为了展示技能持续追问。
