# 工程汇报与总结

把零散的工程材料整理成读者能快速理解、也能据此判断和行动的文字。它适合汇报、项目总结、自评和晋升材料，也适合把已经完成的复盘结论改写给另一类读者。

## 什么时候用

适合这些情况：

- 把会议纪要、项目笔记或妙记整理成管理汇报；
- 把一个项目的过程、结果和取舍写成阶段总结；
- 把成果条目整理成自评、晋升或答辩材料；
- 把已有结论的复盘改写成老板或跨团队伙伴看得懂的版本。

如果还需要判断“为什么会这样”以及下次该保留、改变或停止什么，用 `management-retro`。如果主要问题是指标是否可信，用 `metric-decision`；如果是评审一份尚未实施的方案，用 `tech-review`。

## 工作方式

1. 先弄清楚读者、用途和需要支持的决定。汇报给谁，和谁有权决定、谁负责执行，不一定是同一批人。
2. 从材料中找出背景、目标、关键动作、结果、取舍、风险和协作边界。保留来源、时间范围和数据口径。
3. 区分事实、测量、估算、推断、假设和仍待确认的内容。材料没有说清楚的地方，不用更肯定的措辞填上。
4. 先写结论，再按读者需要补充依据、影响、限制和下一步。结果、动作、判断和建议不要混成一段。
5. 如果缺少量化结果，写清楚目前能确认的定性影响，以及还需要什么数据来支持更强的说法。不要为了让材料显得完整而补造数字、因果或“战略价值”。

事故材料尤其要分开写：已经采取的缓解动作、影响或恢复情况，以及是否已经降低复发风险。做过一个动作，不等于风险已经消失。

素材很散时，先补四件事：给谁看、要支持什么决定、覆盖哪段时间、最想强调结果还是过程。只有这些信息会改变表达时才追问；否则先按现有材料写，并把缺口标出来。

## 常用结构

根据用途选一个够用的结构，不必全部展开：

**管理汇报**：结论 → 进展与结果 → 风险/待决事项 → 下一步和需要的支持。

**项目总结**：背景与目标 → 关键判断和动作 → 结果与影响 → 经验 → 后续选择。

**高管摘要**：需要知道的变化 → 为什么重要 → 当前风险或决定 → 建议动作。

**自评/晋升**：职责范围 → 代表案例 → 结果与影响范围 → 处理的复杂性和取舍 → 可复用沉淀。

如果用户给了字数上限，先按交付语言和约定口径核算，再压缩背景和修饰。不要删掉会改变结论的证据状态、权限边界或限制条件。

## 一个简单例子

原始材料只有：“完成流量切换，服务恢复。”

可以写成：“已完成流量切换，服务恢复时间和剩余影响范围仍需以监控记录确认。下一步核对恢复窗口和触发原因，再决定是否需要补充回退或告警措施。”

这比直接写“问题已解决、风险已消除”更可靠，也更方便读者知道下一步该判断什么。
